# `java.lang.invoke` Design Notes

`java.lang.invoke` is the highest-risk area for modern Java support. Doppio has
Java 8-era method handle and `invokedynamic` machinery, but Java 11+ class files
and libraries rely on more complete linkage, access checks, and dynamic
constant behavior.

## Scope

- Preserve existing Java 8 method handle and lambda tests.
- Add feature probes before changing runtime behavior.
- Treat reflection, nestmates, dynamic constants, and method handles as one
  linked design surface instead of isolated patches.
- Prefer small, native-JVM-compared fixtures that exercise one linkage shape at
  a time. A passing broad fixture is not enough evidence unless each adaptation
  edge is visible in the output.
- Keep class-library shims and runtime fast paths explicitly separate. A shim
  may expose descriptors or nominal constants, but it must not claim executable
  method-handle semantics until the runtime path is tested.

## Work Plan

1. Inventory current native methods in `java.lang.invoke.MethodHandleNatives`,
   `MethodHandle`, and related call-site paths.
2. Add failing fixtures for Java 17 linkage cases:
   - `invokedynamic` string concatenation.
   - private interface methods.
   - method handles crossing nestmate boundaries.
   - dynamic constants when a fixture can produce `CONSTANT_Dynamic`.
3. Define the access-check model shared by reflection and method handles.
4. Implement one linkage shape at a time, keeping method-handle invocation,
   call-site caching, and exception behavior covered by tests.
5. Re-run the existing Java 8 invoke tests after every change.

## Implementation Gates

Each `java.lang.invoke` slice should pass these gates before it is treated as
implemented:

1. **Native fixture first.** Add or extend a `classes/modern_test` fixture and
   verify the native Java 17 output before changing Doppio runtime behavior.
2. **Single linkage shape.** Keep one patch focused on one bootstrap or
   invocation shape: for example `GETSTATIC` return adaptation, virtual method
   receiver handling, varargs collection, or access failure.
3. **Descriptor audit.** Verify stack-slot width, primitive/reference
   descriptors, and bootstrap static argument counts against the generated
   class file. Generated bytecode fixtures must include a native run check.
4. **Access audit.** State whether the slice uses existing class/member access
   helpers, nestmate metadata, or a temporary fast-path bypass. Temporary
   bypasses must be listed under Open Design Questions.
5. **Regression sweep.** Run `grunt --grunt-ignore-compile-errors
   test-modern-java` after the targeted fixture passes, because
   `StringConcatFactory`, `CONSTANT_Dynamic`, records, and sealed classes share
   class loading and bootstrap code.

## Access Model

The runtime should converge on one access helper used by reflection, method
handles, dynamic constants, and record object-method linkage:

- Class visibility should reuse class-loader and package checks that already
  protect ordinary bytecode resolution.
- Member access should accept the caller class, target class, member flags, and
  reference kind. It should explicitly check public/protected/package/private
  rules plus nestmate private access.
- Method-handle lookup modes should be translated into that helper rather than
  duplicated in each bootstrap fast path.
- Until this helper exists, every fast path that bypasses a Java 17 lookup rule
  must remain documented as partial compatibility.

## Runtime Ownership

- `src/ConstantPool.ts` owns class-file bootstrap parsing, bootstrap static
  argument resolution, selected `ConstantBootstraps` fast paths, and the
  current `ObjectMethods.bootstrap` fast path.
- `src/opcodes.ts` owns bytecode invocation of existing method handles,
  especially `invokeBasic` and related stack-slot movement.
- `src/natives/java_lang.ts` owns Java-side native entry points for
  `MethodHandleNatives`, class metadata, and reflection-adjacent helpers.
- `classes/modern_classlib/java/lang/constant` owns nominal descriptor shims.
  These shims can describe targets but should not silently emulate runtime
  invocation without a matching Doppio runtime path.

## Implemented Slices

- Java 17 `MethodHandles.Lookup` has a public same-class fixture covering
  `findStatic` and `findVirtual`, `invokeExact` and loose `invoke` on those
  handles, method-handle type display, and the missing-method
  `NoSuchMethodException` path. The same fixture now covers non-nestmate
  private static/instance lookup failures, same-package package-private
  static/instance lookup success, cross-package public lookup success,
  cross-package subclass protected lookup success, cross-package package-private
  lookup failure, and nestmate private static/instance lookup success. It also
  covers `findStaticGetter`, `findStaticSetter`, `findGetter`,
  and `findSetter` for selected `String` fields under public, package-private,
  non-nestmate private failure, and nestmate private success paths, plus public
  static/instance `int` and `long` fields. It also covers public final
  static/instance setter lookup rejection. Constructor
  lookup is covered for public, package-private, non-nestmate private failure,
  and nestmate-private success paths. A separate reflective lookup fixture
  covers `Lookup.unreflect`, `unreflectConstructor`, `unreflectGetter`, and
  `unreflectSetter` for public members, private non-nestmate access failures,
  and private nestmate method, constructor, static field, and instance field
  success paths. `MethodHandles.privateLookupIn` is covered for same-package
  caller and peer lookup into a target class, private constructor, private
  static/instance method, private static/instance field access, public-lookup
  failure, and primitive/array target rejection. This is currently a minimal
  native overlay on the Java 8 `Lookup` class rather than a complete Java 9+
  lookup-mode implementation. Selected `MethodHandle.asType` success paths are covered for
  reference casts, return widening to `Object`, non-void return dropping to
  `void`, `void` return adaptation to `null` reference, primitive argument and
  return widening, primitive return boxing, and `Integer` to `int` unboxing.
  Selected failure paths cover arity mismatch at adaptation time and runtime
  cast failure. The fixture also covers selected
  combinators: `identity`, `constant`, `bindTo`, `insertArguments`,
  `dropArguments`, `filterArguments`, `filterReturnValue`, `permuteArguments`,
  `guardWithTest`, `catchException`, `exactInvoker`, `invoker`,
  `collectArguments`, `foldArguments`, `explicitCastArguments`,
  `arrayElementGetter`, `arrayElementSetter`, and `throwException`, including
  descriptor-string checks for the adapted shapes. This does not yet claim every
  protected receiver shape,
  every cross-package class-visibility edge, broad `asType` coverage across every primitive/reference conversion,
  broad combinator composition beyond the listed fixture shapes, or executable
  VarHandle behavior.
- Java 12 nominal method-handle descriptors now resolve selected direct
  descriptor shapes by delegating to the existing `MethodHandles.Lookup`
  surface: public same-class static and virtual methods, constructors,
  static/instance field getters and setters, and `asType` wrappers. This is a
  class-library bridge over tested lookup paths, not a new general access
  model.
- Java 17 nominal dynamic-constant descriptors now resolve selected
  `ConstantBootstraps` descriptor shapes in the class-library shim:
  `nullConstant`, `primitiveClass`, `enumConstant`, `getStaticFinal`, and a
  reference plus selected primitive-target `explicitCast` exact and numeric
  conversion paths. It also covers
  selected descriptor-level `ConstantBootstraps.invoke` resolution for public
  static method handles with constant arguments, tested primitive return
  widening, and reference result-cast failure wrapping. This does not claim
  general bootstrap invocation, exact
  `BootstrapMethodError` wrapping beyond the tested bad primitive name, missing
  enum, bad explicit-cast, and bad invoke result-cast failures, exact field lookup failure behavior beyond the tested
  `getStaticFinal` missing-field and wrong-type cases, or `ldc` interoperation
  beyond the existing runtime fast paths.
- Java 9 `StringConcatFactory` call sites have a targeted fast path for basic
  `makeConcat` and `makeConcatWithConstants` recipes, including tested static
  recipe constants for `String`, primitive numeric values, and `Class`
  constants covering ordinary classes, interfaces, and arrays. The fast path
  now maps raw operand-stack words back to descriptor parameters for tested
  wide-slot `long` concat arguments, including adjacent `long` parameters and a
  `long` followed by a reference parameter. It also handles tested boxed
  primitive object arguments for `Integer`, `Long`, `Boolean`, and `Character`
  without invoking arbitrary Java `toString()` code, plus one observable user
  object `toString()` dispatch and one null reference concat.
- Java 11 `CONSTANT_Dynamic` parsing and `ldc` resolution have a targeted fast
  path for selected `java.lang.invoke.ConstantBootstraps` methods:
  `nullConstant`, `primitiveClass`, `enumConstant`, `getStaticFinal`, and
  reference-typed plus tested primitive-target `explicitCast`.
- `ldc2_w` resolves and loads long and double `CONSTANT_Dynamic` entries for
  the tested `explicitCast` paths.
- Primitive `explicitCast` handles selected cross-wrapper casts among
  `Integer`, `Long`, `Float`, and `Double` constant-pool arguments using Java
  primitive conversion rules.
- `ConstantBootstraps.invoke` has targeted fast paths for selected method-handle
  targets. The current fixture covers a no-argument static method returning a
  reference dynamic constant, a `GETSTATIC` field getter returning a reference
  dynamic constant, a static method with an integer static argument returning a
  primitive `int`, a `REF_invokeStatic` interface method target returning a
  reference dynamic constant, a `NEWINVOKESPECIAL` constructor handle returning a
  reference dynamic constant, an `INVOKEVIRTUAL` target that receives its
  receiver from the bootstrap static arguments and returns a primitive `int`,
  a `REF_invokeInterface` target that receives its receiver from the bootstrap
  static arguments and returns a primitive `int`, a `GETFIELD` target whose
  receiver is supplied by another dynamic constant, a `REF_invokeSpecial`
  target whose receiver is supplied by another dynamic constant and whose
  private instance method returns a reference dynamic constant, a `PUTSTATIC`
  target that writes a `String` static argument and returns `null` into a
  reference dynamic constant, and a receiver-backed `PUTFIELD` target that
  writes a `String` static argument and returns `null` into a reference dynamic
  constant, plus a `PUTSTATIC` double field setter fed by a `CONSTANT_Long`
  static argument and verified by double getter, boxed getter, and double
  arithmetic paths. Static
  and virtual/interface method targets,
  `GETSTATIC`/`GETFIELD` field targets, and constructor targets also perform
  reference result cast checks for the tested non-exact return cases where a
  `String` or `StringBuilder` result backs an `Object` dynamic constant. Static
  method targets and `GETSTATIC`/`GETFIELD` field targets also cover the tested
  primitive boxing case where an `int` result backs `Integer` and `Object`
  dynamic constants. Static method targets cover tested argument adaptation
  cases where a `CONSTANT_Integer` bootstrap static argument is boxed for an
  `Integer` method parameter, an `Integer` dynamic constant is unboxed for an
  `int` method parameter, an `Integer` dynamic constant is widened for a
  `long` method parameter, a `CONSTANT_Integer` static argument is widened for
  a `long` method parameter, and trailing `String` static arguments are
  collected into a `String[]` for a tested `ACC_VARARGS` method target. A
  second `ACC_VARARGS` method target covers a trailing `CONSTANT_Integer`
  static argument widened into a `long[]` component before the method returns
  that value. Method targets also cover the tested primitive return widening
  case where an `int` target return backs a `long` dynamic constant, and
  `GETSTATIC` field targets cover the tested case where an `int` field value
  backs a `long` dynamic constant.
  Static method targets also cover the tested `void` return case where the
  reference dynamic constant result is `null`.
- Java 16 records have a targeted `java.lang.runtime.ObjectMethods.bootstrap`
  `invokedynamic` fast path for compiler-generated field component handles,
  covering generated `toString`, `equals`, and `hashCode` in the current record
  fixture, including selected `float`/`double` component parity for `NaN` and
  signed zero.

## Open Design Questions

- Whether to emulate Java 17 `MethodHandles.Lookup` access modes exactly or map
  them onto Doppio's existing class/member access helpers first.
- `MethodHandles.privateLookupIn` currently injects a native method into the
  Java 8 `MethodHandles` class and grants Java 8 full private/package lookup
  modes for accepted classpath targets. It does not yet expose Java 9+
  `Lookup.MODULE`, `UNCONDITIONAL`, `ORIGINAL`, `previousLookupClass`, or
  `dropLookupMode` parity.
- Whether broad `MethodHandleDesc.resolveConstantDesc` should rely entirely on
  `Lookup` once access checks converge, or keep descriptor-specific guards for
  unsupported handle kinds and cross-package/protected receiver shapes.
- Whether `DynamicConstantDesc.resolveConstantDesc` should eventually route
  through executable bootstrap method handles for all descriptors, or keep
  selected `ConstantBootstraps` branches in the shim until the runtime bootstrap
  path is complete.
- How much of the Java 17 JDK `java.lang.invoke` implementation can be reused
  with the existing Java 8 class library image.
- `MethodHandleNatives.resolve` currently bridges Java 11 nestmate private
  `find*` lookup through `MemberName` access-flag adjustment, and the modern
  `sun.invoke.util.VerifyAccess` shim bridges `unreflect*` lookup access
  checks. Revisit both once the lookup class-library layer is replaced or a
  shared Java 17 access helper exists.
- Whether dynamic constants beyond the selected `ConstantBootstraps` fast paths
  should resolve through a shared bootstrap path or through more per-bootstrap
  fast paths until the class library has Java 11 `ConstantBootstraps`.
  Primitive `explicitCast` currently covers `boolean`, `byte`, `char`, `short`,
  `int`, `long`, `float`, and `double` descriptor targets for the tested
  constant-pool argument shapes, including selected cross-wrapper primitive
  casts but not the full Java wrapper conversion matrix.
- The `ConstantBootstraps.invoke` fast path does not yet cover broad dispatch
  adaptation beyond the targeted virtual/interface/special receiver cases and
  tested interface static method target, remaining
  field setter shapes beyond the tested reference `PUTSTATIC`, primitive
  `PUTSTATIC` `CONSTANT_Long` to `double`, and receiver-backed reference
  `PUTFIELD` cases, varargs adaptation beyond the tested reference-array
  collection and `CONSTANT_Integer` to `long...` widening cases, full primitive boxing/unboxing parity beyond the tested
  `int` return, `CONSTANT_Integer` argument boxing, `Integer` argument
  unboxing, `Integer` to `long` argument widening, `CONSTANT_Integer` to
  `long` argument widening, method-target `int` to `long` return widening, and
  `GETSTATIC` field-target `int` to `long` return widening cases, or non-exact
  return adaptation beyond the targeted
  method/field/constructor reference result cast cases and the tested
  method/field `int` return boxing plus method-target `void` to reference
  `null` cases.
- The record `ObjectMethods.bootstrap` path currently bypasses the JDK helper
  class and only supports field-backed record components. It does not implement
  general `ObjectMethods` linkage, arbitrary method-handle components, or
  reflection metadata.
- `StringConcatFactory` object/reference arguments still need broader
  `String.valueOf(Object)` coverage beyond the tested boxed primitive wrappers,
  observable user object, and null reference concat.
